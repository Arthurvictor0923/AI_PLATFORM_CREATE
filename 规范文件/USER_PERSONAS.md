## 一、画像总览

### 1.1 平台定位（实施方案 §1.1.4.1）

> 以**全重实验室及合作高校科研团队**为核心服务对象，采用**邀请制注册**与资源按需调配机制。用户规模根据科研任务动态调整，重点保障核心用户在算力供给、数据供给、模型部署、模型服务等方面的资源倾斜，确保平台资源向高价值研发活动集中。

> 协同创新平台定位为农业算法研发与成果转化支撑平台，主要服务于**全重实验室、信息公司及受邀科研合作单位**开展算法研发、模型验证和成果转化工作。平台采用受邀注册机制，**不面向社会公众开放**，不提供开放注册、数据共享交换及公众上传服务。平台用户主要为**实验室科研人员、信息公司技术人员以及合作高校、科研院所等科研团队成员**。（实施方案 §4.4.1）

### 2.3 数据隔离与授权

> 实施方案 §4.4.1：平台实行**分级授权管理制度**，用户须通过受邀注册并经管理员审核后方可获取平台访问权限。平台数据使用遵循 **"最小必要、按需授权"** 原则。

| 级别 | 含义 | 覆盖功能 |
|------|------|---------|
| 🔴 **单位级隔离** | 租户 A 看不到租户 B 的数据 | 镜像、模型元数据、推理服务、数据集、算子、工作流、智能应用、执行历史、需求 |
| 🟡 **用户级隔离** | 同单位不同用户互不可见 | 开发作业（容器实例） |
| 🟢 **公开/广场** | 显式发布后全员可见 | 模型广场、应用市场 |
| ⚪ **无需隔离** | 全局共享 | 平台预置镜像、系统配置 |

**关键规则**:
- 跨单位可见的**唯一窗口**是广场/市场
- 数据集是最高敏感级，**不存在默认公开通道**
- 数据不出域、不上云，合作方不得复制、下载、传播或向第三方提供
- 项目合作终止后，相关授权即时收回
- 撤回 ≠ 删除（广场下架但数据保留）

## 三、业务画像（以实施方案为准）

> 本章以 `协同创新平台实施方案_v5_0701.md` 为权威来源，按实施方案中的用户群体划分。

### 3.1 科研人员（核心用户）

**实施方案依据**:
- §1.1.4.1: "以全重实验室及合作高校科研团队为核心服务对象"
- §4.4.1: "平台用户主要为实验室科研人员、信息公司技术人员以及合作高校、科研院所等科研团队成员"
- §2.2.2.1: 协同服务门户是"科研人员访问平台的唯一入口"，围绕"数据找得到、模型看得见、成果调得动"的核心目标

科研人员是平台存在的根本原因。实施方案将平台要解决的三大瓶颈全部围绕科研人员的痛点展开：数据获取壁垒（§1.1.3 第一）、模型碎片化（§1.1.3 第二）、成果转化堵塞（§1.1.3 第三）。

#### 3.1.1 全重实验室科研人员

| 属性 | 描述 |
|------|------|
| **身份** | 智慧农场技术与系统全国重点实验室的研究员、算法工程师 |
| **所属单位** | 全重实验室（北大荒集团 + 哈尔滨工业大学 + 东北农业大学共建） |
| **核心工作** | 农业算法模型的研发、训练、微调、验证 |
| **技能水平** | 高 — 深度学习框架、Python、容器技术、遥感影像处理 |
| **使用频率** | 高 — 日常研发环境 |
| **平台价值** | 从"数据拿不到、模型散在外、成果落不下"→"数据找得到、模型看得见、成果调得动" |

**关键业务路径**:

```
登录 → 开发空间（创建 Notebook → 调环境 → 产出镜像）
    → 模型管理（新增模型元数据 → 部署推理服务）
    → 模型中心（同步至模型广场，对外可见）
    → 需求大厅（查看科研课题/技术开发需求 → 评估认领）
    → 数据中心（检索数据集 → 申请下载 → 用于训练）
```

**核心工具**: 开发空间（JupyterHub + VS Code Server）、镜像管理、模型部署、工作流编排（X6）

**产出物**: 自定义镜像、模型元数据、推理服务、算子、工作流、智能应用

**对应系统角色**: R3 开发者（研发人员）、R2 单位管理员（实验室 PI / 课题组长）

**痛点（实施方案 §1.1.3）**:
1. 数据获取壁垒高筑 — 4A 通道路径冗长，"能看不能用、能用不便用"
2. 模型资产碎片化 — 验收后分散在个人手中，缺少统一纳管与协同编排
3. 成果转化堵塞 — 模型验收后闲置，未变成可发现、可调用、可复用的服务

#### 3.1.2 合作高校与科研院所团队

| 属性 | 描述 |
|------|------|
| **身份** | 哈尔滨工业大学、东北农业大学等合作高校的课题组成员，以及其他受邀科研院所的研发人员 |
| **所属单位** | 各合作高校、科研院所（通过"关于平台→入驻申请"加入） |
| **核心工作** | 基于平台数据和算力开展联合研发、模型验证 |
| **技能水平** | 中–高 |
| **使用频率** | 中 — 按合作项目周期 |
| **访问方式** | 受邀注册 → 管理员审核 → 分级授权（按项目范围控制权限） |
| **对应系统角色** | R3 开发者 |

**区别于全重实验室人员**:
- 受单位级数据隔离约束，仅可访问本单位数据和已授权的平台资源
- 可在所参与科研项目范围内使用平台数据资源和算力资源，不得用于非约定用途（实施方案 §4.4.1）
- 项目合作终止后，相关授权即时收回

### 3.2 平台运营人员

**实施方案依据**:
- §3.1: "平台运维工作由北大荒信息有限公司负责，设立专职运维团队"
- §4.4.1: "平台用户主要为实验室科研人员、**信息公司技术人员**以及合作高校、科研院所等科研团队成员"

#### 3.2.1 运维团队

| 属性 | 描述 |
|------|------|
| **身份** | 北大荒信息有限公司技术团队 |
| **编制** | 运维负责人 1 名 + 系统运维工程师 2 名 + 数据管理员 1 名（实施方案 §3.1） |
| **核心职责** | 7×24 小时监控、故障分级响应、数据备份、安全管理、平台升级迭代 |
| **技能水平** | 高 — 系统运维、容器化部署、GPU 资源调度 |
| **使用频率** | 高 — 日常运维 |
| **对应系统角色** | R1 超级管理员 |

**日常运维内容（实施方案 §3.2）**:

| 工作项 | 说明 |
|--------|------|
| 系统监控 | 7×24 小时监控服务器资源使用率、网络状态、应用服务状态 |
| 故障处理 | 一级（系统不可用）1h 响应 / 二级（功能异常）4h 响应 / 三级（性能下降）24h 响应 |
| 数据备份 | 每日增量 + 每周全量，保留 90 天 |
| 安全管理 | 定期漏洞扫描 + 每年 ≥1 次数据安全审计 |
| 平台升级 | 每季度一次功能更新，重大更新前充分测试和用户验收 |

**核心工具**: 系统管理（用户/角色/单位 CRUD）、资源总览仪表盘、服务监控、运营管理后台（首页管理/栏目管理/入驻管理/审核管理/数据管理/标签管理）

#### 3.2.2 审批与管理人员

| 属性 | 描述 |
|------|------|
| **身份** | 信息公司管理员、各入驻单位管理员 |
| **核心职责** | 审批模型使用申请、数据集下载申请、机构入驻申请、需求审核 |
| **审批原则** | "最小必要、按需授权"（实施方案 §4.4.1） |
| **使用频率** | 低–中 — 按申请触发 |
| **对应系统角色** | R1 超级管理员（全局审批）、R2 单位管理员（本单位审批） |

**审批流转规则**:
- 资源所有权为个人 → 审批流向资源所有者
- 资源所有权为平台 → 审批流向管理员
- 审批工作流引擎跨模块复用（模型申请 / 数据下载 / 需求审核）

### 3.3 入驻机构用户

**实施方案依据**:
- §2.2.2.1 关于平台: "提供机构入驻申请入口，支持**科研院校、农场、企业**等不同机构类型，入驻申请由基础平台进行审核管理"
- §1.1.4.3: 平台建成后"持续为科研院所、农场、企业及相关用户提供模型调用、数据分析、在线开发等服务"

#### 3.3.1 科研院校用户

| 属性 | 描述 |
|------|------|

| **入驻方式** | 以院校为单位提交入驻申请 → 管理员审核 → 单位级授权 |
| **核心活动** | 利用平台数据 + 算力开展课题研究、模型开发、论文实验 |
| **权限范围** | 单位级隔离，仅可访问本单位数据和已授权平台资源 |

#### 3.3.2 农场用户

| 属性 | 描述 |
|------|------|
| **身份** | 北大荒集团下属农场的技术人员、业务人员 |
| **入驻方式** | 以农场为单位提交入驻申请 → 管理员审核 |
| **核心活动** | 浏览模型中心找到适用的农业 AI 模型，申请使用，集成到农场业务系统 |
| **技能水平** | 低–中 — 熟悉农业生产业务，不要求编程或 AI 技术背景 |
| **使用频率** | 低–中 — 按需使用 |
| **对应系统角色** | R5 农场用户 |

**消费路径**:

```
登录 → 模型中心（浏览/筛选/查看详情）
    → 申请使用（提交申请 → 审批 → 获得授权）
    → ① 部署推理服务，获取 API 对接农场现有系统
      ② 运行工作流，上传数据获取分析结果
      ③ 直接使用智能应用，打开网页即用
    → 数据中心（检索农业数据集 → 申请下载）
    → 需求大厅（发布数据标注/技术开发需求）
```

**关键设计约束**:
- 不涉及编程操作，不访问开发空间
- 内部协作不涉及金钱交易（预算/报价字段不适用）
- 实施方案明确"平台不涉及农场经营主体或个人用户数据的汇聚和流转"（§4.4.1）

## 四、机构类型与用户映射

> 实施方案 §2.2.2.1 关于平台列出三种入驻机构类型；§4.4.1 明确了平台用户的具体构成。

```
                    平台用户（实施方案 §4.4.1）
                    ├── 全重实验室科研人员 ──── 核心开发力量
                    ├── 信息公司技术人员 ──── 平台运营方
                    └── 合作高校/科研院所团队 ── 联合研发力量
                              │
                    入驻机构（实施方案 §2.2.2.1）
                    ├── 科研院校 ── 高校课题组、研究院所
                    ├── 农场     ── 北大荒下属农场
                    └── 企业     ── 农业科技企业
                              │
                    外部协作（实施方案 §4.4.1）

```

## 八、C/B/G 端定位

> 分析平台在消费者端（C）、企业端（B）、政府端（G）三个维度的定位。

| 端 | 是否涉及 | 说明 |
|:--:|:--:|------|
| **C端**（个人消费者） | ❌ **不涉及** | 实施方案 §4.4.1："不面向社会公众开放，不提供开放注册" |
| **B端**（企业/机构） | ✅ **核心** | 全重实验室、合作高校、科研院所、农场、企业 |
| **G端**（政府） | ✅ **涉及** | 政府机关作为数据合规消费者，使用深度有限 |

**关键结论**: 平台是企业级 B2B 受邀制平台，而非 C 端公开平台。这决定了：
- 无开放注册、无实名认证、无社交登录
- 功能清单中从魔搭社区（C 端平台）抄来的个人认证、评价体系、竞标报价等全部砍掉
- 需求大厅是"内部协同"而非"公开市场撮合"

## 九、账号生命周期

> 平台采用受邀注册制，个人无法自助创建账号。

```
机构入驻申请 → 管理员审核 → 为机构成员创建账号 → 用户登录使用
  (关于平台)     (后台审批)    (超级/单位管理员)    (受邀用户)
```

1. 机构通过「关于平台」页面提交入驻申请（支持**科研院校、农场、企业**三类）
2. 平台管理员审核机构资质
3. 审核通过后，超级管理员或单位管理员在系统管理后台为机构成员逐一手动创建账号
4. 用户收到账号密码 → 登录 → 进入门户已登录视图
5. 项目合作终止后，相关授权即时收回（实施方案 §4.4.1）

**门户体现**:
- 只有「登录」按钮，**没有「注册」按钮**
- 登录卡片底部说明："还没有账号？平台采用受邀注册制，请先通过机构入驻申请"
- 关于平台弹窗完整说明入驻流程
- 未登录快捷入口点击后跳转登录页（而非注册页）

**不需要的功能**（已确认砍掉）:
- 个人自助注册、手机号/邮箱注册
- 个人实名认证（上传身份证）、企业认证（上传营业执照）
- 绑定第三方账号（微信/支付宝/GitHub）
